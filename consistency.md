# Сверка диаграмм — журнал согласованности

## Правило 1: каждый вызов соответствует операции получателя

| Вызов | Получатель | До исправления | Решение |
|---|---|---|---|
| найтиСвободные | СервисБронирования | Да | Оставить |
| получитьЗанятость | Расписание | Да | Оставить |
| свободна | Аудитория | Нет (`isFree`) | Переименовать операцию в `свободна` |
| создатьБронь | СервисБронирования | Да | Оставить |
| пересекаетсяС | Бронь | Нет (`overlaps`) | Переименовать операцию в `пересекаетсяС` |
| сохранить | ХранилищеБроней | Нет класса | Добавить получателя/операцию `сохранить` |
| отправить | СервисУведомлений | Нет класса | Добавить получателя/операцию `отправить` |

## Правило 2: каждый участник — класс или актор

| Участник | Есть на исходной схеме? | Решение |
|---|---|---|
| Сотрудник | Да | Класс и роль пользователя |
| СервисБронирования | Да | Класс |
| Расписание | Да | Класс (внешний источник данных) |
| Аудитория | Да | Класс |
| Бронь | Да | Класс |
| ХранилищеБроней | Нет | Добавить класс как инфраструктурного получателя |
| СервисУведомлений | Нет | Добавить класс как инфраструктурного получателя |

## Журнал исправлений

1. `свободна`: операция Аудитории названа `isFree` — привести имя к `свободна`, поскольку последовательность использует именно его.
2. `пересекаетсяС`: у Брони есть `overlaps` — переименовать, сохранив семантику проверки конфликта.
3. `сохранить`: ХранилищеБроней отсутствует — добавить отдельную сущность и операцию сохранения, т. к. у вызова должен быть получатель.
4. `отправить`: СервисУведомлений отсутствует — добавить отдельную сущность и операцию, т. к. отправка выполняется вне предметного объекта Бронь.

Все решения — проектная сверка с предоставленной последовательностью, не подтверждение заказчиком новой функциональности.
